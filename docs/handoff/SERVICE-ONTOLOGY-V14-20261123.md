| 단계 | 내용 |

| 2. 원인 | 이 문서들은 문서 버전 관계(`recordedByDocumentVersion`)를 갖는다. v1.3 T-Box는 이 관계를 업무 기록(`BusinessRecord`: 도착·출하·생산 실적처럼 일어난 일의 기록)만 갖게 했다. 그래서 추론이 "견적은 업무 기록이다"라는 결론을 냈다. |

| 4. 수정 | T-Box 새 판 `ontology-v1.4`를 만들었다. 원본 v1.3은 그대로 두었다(아래). |
| 5. 재측정 | 같은 측정기(`dev/measure_reasoning.py --schema-slot`)·같은 원장(v1–v23)으로 다시 쟀다. 깨끗한 원장의 불일치 6 → 0, 탐지율은 그대로(아래). |

## T-Box 변경 (v1.3 → v1.4)

| 변경 | 뜻 |
|---|---|
| `VersionedEntity`(버전 기록 대상) 추가, `BusinessRecord ⊑ VersionedEntity` | 문서 버전으로 남는 것의 공통 상위 종류 |
| `BusinessDocument`(업무 문서) 추가 | `PurchaseRequest`·`SupplierOffer`·`PurchaseOrder`·`ScenarioRun`·`SourceDocument`를 그 아래에 둔다 |
| `BusinessDocument owl:disjointWith BusinessRecord` | 문서와 일어난 일의 기록은 다르다. 시나리오 가정은 원장 사실이 될 수 없다(DEC-H57)는 규칙이 T-Box에도 들어간다. |
| `recordedByDocumentVersion` domain: `BusinessRecord` → `VersionedEntity`, 라벨 "사건 문서 버전" → "문서 버전" | 업무 문서도 버전 관계를 가질 수 있다 |
| SHACL `Shape_recordedByDocumentVersion`: `sh:class BusinessRecord` → `VersionedEntity` | 위와 같은 범위 |

- 클래스는 52개에서 54개가 되고, 관계 74개·shape 79개는 그대로다. 투영 매핑(`MAPPING_VERSION`)도 바꾸지 않았다.
- `ScenarioRun`·`SourceDocument`도 업무 문서에 넣었다. 지금 코드에서 SCENARIO·SUBSTITUTION 문서가 이 두 종류로 투영되며 같은 관계를 가지기 때문이다. 이번 시연 원장에는 이 두 문서가 없어 불일치로 나오지 않았을 뿐, v1.3에서는 쓰는 순간 같은 불일치가 났을 것이다.
- v1.3 슬롯은 검증 보고서 파일(`shacl_report.ttl`, 2 triple)도 shape로 함께 읽었다. v1.4 슬롯에는 shape 파일만 있어 shape triple 수가 604에서 602로 줄었다. 검사 내용에는 영향이 없다.

## 비공개 자료를 다룬 방법

- 새 판은 저장소 밖 비공개 입력 폴더에 `ontology-v1.4/`(tbox·shapes·adapters·CHANGELOG)로 따로 두었다. v1.3 파일은 읽기만 했고, 쓰기 전후 해시가 같은지 확인했다.
- 원본 목록(`SOURCE_MANIFEST.json`)에 `ontology-v1.4` 슬롯 항목 4개를 추가했다. 기존 155개 항목은 바이트 단위로 그대로이고, 추가 전 사본도 같은 폴더에 남겼다.
- 앱은 `--schema-slot`(기본 `full-delivery-v1.3`)으로 읽을 판을 고른다. 8874 실행 스크립트(저장소 밖)만 `ontology-v1.4`를 쓰게 바꿨고, 바꾸기 전 사본을 남겼다.

## 스키마가 바뀌었을 때의 그래프 검사

이미 통과(READY)한 검사 결과는 덮어쓰지 않는다는 기존 규칙이 있다. 이 규칙은 최소한으로만 넓혔다.

- 앱이 시작될 때 각 원장(run)의 **최신 버전만** 새 스키마로 다시 검사한다(`LedgerReader.pending(ontology_version)`). 이전 버전들은 검사받은 스키마의 결과를 그대로 둔다.
- READY 결과는 **스키마 판이 다르고 새 검사도 통과했을 때만** 교체한다. 교체 전 결과는 RDF까지 `service_projection_history`(migration 015)에 그대로 남는다. 그래서 이전 답변이 인용한 검사 결과를 그 스키마 그대로 추적할 수 있다.
- 같은 스키마로 결과를 바꾸는 것과 통과하지 못한 결과로 덮는 것은 전처럼 `READY_PROJECTION_IMMUTABLE`로 막는다.

# 데이터 초기화·시연 실행·기대 결과 분리 계약

상태: 2026-11-08 INITIAL 변환·초기 원장 조회 slice 구현. `service/imports.py`는 허용된 기초 잔액만 변환하고 `service/ledger.py`가 개발용 PostgreSQL 원장에 반영한다. 전체 bundle의 업무 명령 실행·BOM 등록·후속 원장 재생은 미구현이다. 실제 증거는 [SERVICE-INITIAL-20261108](SERVICE-INITIAL-20261108.md)을 따른다. 본 문서는 기존 데이터 역할·전체 수용 계약을 유지하며 원문·fixture·운영 원장을 변경하지 않는다.

## 1. 기준과 입력 자료

공식 요구·아키텍처는 [입력 자료 목록](SOURCE_INDEX.md)의 `SRC-V17-01` 원본·식별·생산·이행·추적·승인 요구 및 `SRC-V17-03` §3·§7·§12를 따른다. 첫 범위는 `SRC-PLAN`의 `PHASE_1_SCOPE.md`다. 전체 v1.7 요구·기존 CQ20개·추가 C/D 후보를 이 자료 하나로 대체하지 않는다.

원문은 공개 저장소 밖의 별도 `private_inputs`에 둔다. 실행 환경은 `PRIVATE_INPUT_ROOT`와 [입력 자료 목록](SOURCE_INDEX.md)의 manifest로 위치·SHA-256을 해석한다. 아래 이름은 **논리 입력 슬롯**이며, 저장소 루트나 개발자의 절대경로를 데이터 계약에 고정하지 않는다. 원문 자료가 Cloud 작업공간에 자동 전달된다고 가정하지 않는다.

| 슬롯 | 원자료·역할 | 사용 경계 |
|---|---|---|
| `mk-s2` | MK-S2 HTML, fixtures, 데이터 구조·백엔드 규약·용어집 | 화면·동선·기초 합성 원장 기준. HTML의 메모리 상태를 서버 원장으로 취급하지 않음 |
| `v1.7-data` | `data/raw`, `normalized`, `source_manifest.json`, 검수 대기·출처 문서 | 실제 공개 BOM 원문과 구조 파싱 결과. 공개 원문이라는 사실과 기술 승인·재배포 검토는 별개 |

| `full-delivery-v1.3` | `data/bundle.json`, assumptions·scenario_runs·expected_results, ontology·verification | 전체 고객 도착 시연의 **원천 검증 자료**. 서비스 DB 초기 seed가 아님 |

사용자는 공개 저장소 유지와 원본 별도 보관을 확정했다. 공개 저장소에는 이 원문·혼합 데이터를 업로드하지 않는다. 개인 gold·평가 원답·원시 trace·비밀은 기존 정책대로 Git 밖에 둔다. 공개용 평가 코드·검토된 합성 fixture와 원본 자료를 구분한다.

## 2. 세 가지 데이터 모드

| 모드 | 적재·사용할 내용 | 넣지 않을 내용 | 검증 |
|---|---|---|---|
| `INITIAL` | 원본 출처·필요 기준정보, 승인되지 않은 BOM 상태, 기초 합성 집계·재고·예약·견적 후보 | 미래 PR/PO·입하·합격·장착·생산·출하·도착·합성 승인·완료 관계 | 시작 CQ에서 잔여68, BOM 미등록 보류, 신규 LOT의 가용0, 신규 장착0 |
| `COMMANDS` | 사용자 선택 후 실행할 typed 명령과 사건의 기대 순서·허용 입력 | `POSTED_DESIGN`을 실제 POSTED로 바로 복사, 저장된 승인 fixture를 실제 승인으로 사용 | 서버 신원·승인·정확버전·멱등 검증 후 서비스가 사건 생성 |
| `EXPECTED` | 시점별 수량·경로·거절·UNKNOWN 기대값, 오프라인 검증 보고서 | Agent의 검색 문맥·정답 입력·운영 조회 데이터 | 도구·DB에서 계산한 실제 결과와 독립 비교. 정답 누출 금지 |

현재 INITIAL 변환은 `cq-v1.1`의 기초 잔액을 명시적 allowlist로 읽고 입력 hash·변환기/원천 버전·회사/profile/run 및 canonical ID를 보존한다. `partition_reference_bundle`은 COMMANDS 후보와 EXPECTED를 별도 객체로 분리하지만 후보를 실행 가능한 명령이나 실제 승인으로 승격하지 않는다. 전체 업무별 변환·실행/대사는 남아 있다. 기존 `analysis_tools/build_dataset.py`를 DB seed로 실행하지 않는다.

`bundle.entities`에는 새 보드·미래 사건·완료 관계·승인 기대값이 함께 들어 있다. `events`만 걸러서 나머지 `entities`·`relationships`를 모두 초기 적재하는 방식도 금지한다. 초기 객체·필드·관계는 **허용 목록과 유효/인지 시점**으로 분리한다. 미래 계획은 필요할 때 별도 계획/후보 상태로 표시하며, 이미 관측된 사실이나 확보 재고로 조회되지 않아야 한다.

## 5. 계산·구매·후속 이행의 연결

확정된 시연 비교는 양품 목표40, 기본 투입40, 계획수율94%에서 `ceil(40 / 0.94)=43` 투입이다. 같은 기준 재고20과 동일 BOM 단위1을 적용해 `max(40−20,0)=20`, `max(43−20,0)=23` 부족을 비교한다. 과거93.75%와 새94%를 같은 설정에 덮어쓰지 않는다.

사용자가 예측안을 선택해 23개 PR 초안을 만들고, 별도 검토·승인·발주·입하·검수·가용 전환을 거친다. 내부 발주 확정은 실제 공급사 송신·납품 확약이 아니다. MOQ/주문배수·운임·견적 유효기간을 검사하고 미확인 비용을0으로 처리하지 않는다. IM-0017 재고120은 대체 승인 전 확보량0이다.

v1.3에서 IM-0016 외 `SYN-ITEM-L1-001/012/045`도 부족하므로 전체 BOM 계산에서 숨기지 않는다. IM-0016만 확보하고 전체62개 적용 행을 충족했다고 답하면 실패다.

입하23개와 검사합격23개는 별도 사건이다. 검사대기 때는 가용 증가0, 합격 후 IM-0016 품목 보유73/타예약30/가용43이다. LOT별로 기존50·신규23을 유지한다. 과거 MK-S2의 `LOT-PWR-01 on_hand=73` 표기는 품목 합계와 LOT 혼용이므로 서버 계약에서 분리한다.

| 시점 | 양품 | 완성품입고 | 출하 | 도착 | 잔여 약속 |
|---|---:|---:|---:|---:|---:|
| 초기 | 60 | 50 | 35 | 32 | 68 |
| 기존 3→2→1과 일치하는 중간점 | 63 | 53 | 37 | 33 | 67 |
| 전체 성공 fixture의 끝 | 100 | 100 | 100 | 100 | 0 |

1차 자재 확보 서비스 인수에서는 후속 생산·장착·출하·도착 사건을 자동 진행하지 않는다. 새 도착 사건이 없다면 잔여 약속은68이다. 전체68대 고객 도착과 중간3→2→1은 후속 T15~T17 등의 보존된 인수 범위다.

전체 v1.3의 합성 결말은 **실제 투입40·양품40·신규불량0**, 계획43 중3개 미사용이다. 43개를 이미 생산 투입하거나 3개 불량을 확정하는 뜻이 아니다. 이 결말은 아직 제안된 시연 기본안이며, 94% 계산이 양품40을 보장한 결과로 표현하지 않는다. 시연 사건이 실제 서비스에서 기록된 뒤에는 `합성 시연 · 양품40 확보 완료`, 최종 `고객 도착100/100 · 잔여0`로 명확하게 표시한다.

v1.3 최종 장착에서 신규 LOT23개는 보드001~023에 사용되고, 기존 LOT에서17개를 소비한다. 최종 신규 LOT잔고0, 기존 LOT잔고33(타예약30·가용3)이다. 따라서 여유3개를 신규 LOT 잔고3으로 표시하지 않는다. 중간3→2→1 이후 다른 배치가 진행되므로 그 시점의 자재 원장은 v1.1 단독3대 실행과 항상 같지 않다.

## 6. 사건·시간·실행 격리

입하, 검사, 예약, 소비, 장착, 생산완료, 완성품입고, 배정, 출하, 도착은 별개 사건이다. 실제 차감은 소비에 한 번 발생하며 장착 관계를 생성하면서 다시 차감하지 않는다. 사건별 board/lot/job/round·문서 버전/hash·근거·`effective_at`·`recorded_at`·원장 버전·idempotency key를 연결한다.

- 질의 계약은 회사/권한, profile/run, 업무 대상, `as_of`, `known_as_of`, 원장/투영/온톨로지/규칙 버전을 고정한다. 역사 조회에서 미래에 알게 된 근거를 사용하지 않는다.
- `RUN-FULL-001`은 정상 합성 실행, `RUN-LATE-001`·`RUN-MISSING-001`은 실제 원장 쓰기0인 비교 실행, `RUN-INVALID-*`는 거절돼야 하는 입력이다. run별 그래프 합집합을 현재 재고·납품 실적으로 계산하지 않는다.
- 늦은 실행은 최종100대 도착해도38대 기한 지연이다. 누락 실행은 UNKNOWN이며 정상0으로 표시하지 않는다.
- 같은 시각의 사건은 문자열 ID 정렬만으로 결정하지 않고, 명시된 의존 관계·서버 순서로 처리한다. 소비는 예약·검사 이후, 도착은 대응 출하 이후여야 한다.
- reset은 전용 테스트 회사·run에서만 허용하고 운영 원장 삭제와 구분한다. 새로운 실행은 새 run을 부여하고, 고정 seed와 입력 hash로 결과를 비교한다.
- 원장 변경은 새 서버 승인·반영을 거친다. What-if에서 payload가 바뀌면 기존 승인을 재사용하지 않는다.

INITIAL 생성·개발 원장 반영은 현재 slice로 구현했으며, 후속 명령 fixture의 실행 변환·재생/대사는 별도 작업이다. 원자료의 `POSTED_DESIGN`, `actual_execution=false`, `real_service_execution=false`를 바꾸는 것만으로 실행 증거가 되지 않는다.

## 7. ID와 Triple 이행 규칙

같은 표시ID라도 회사·원천·프로필·객체 종류가 다르면 자동 병합하지 않는다. v1.3의 `RUN-FULL-001:Class:display_id`는 보존하고, 서버 canonical ID와의 명시적 crosswalk 및 migration 버전을 둔다. 표시ID를 승인 키·전역 PK로 사용하지 않는다.

| 충돌·변환 대상 | 처리 방향과 실패 기준 |
|---|---|
| 주문 `ORD-26041` / 납품회차 `ORD-26041-01` | 별개 클래스, `roundOfOrder`로 연결. 질의 대상을 문장만으로 임의 교체하지 않음 |
| MK IM-0008 / 참고 v2.6 IM-0008의 서로 다른 품목 의미 | source namespace 분리·검토 crosswalk. 같은 문자열로 재고·부품 병합 시 실패 |
| MK IM-0016 / 기존 PART-TPS의 서로 다른 부품 의미 | 서로 다른 부품. 승인·LOT·변경 영향을 공유하지 않음 |
| 같은 RefDes U3 또는 EVB의 중복 `Ref**` | 구성·원문 snapshot·BOM 행·occurrence로 식별. 이름만으로 전역 위치 생성 금지 |
| `installationUsesLot` → RDF `usesLot` 등 | `ontology/predicate_adapters.json`에 따른 명시 adapter. 원문 술어와 방향·근거 보존 |
| `HAS_LOT`가 양방향으로 쓰인 목업 간선 | `PartLot —lotOf→ InternalItem` 등 검토된 방향으로 통일하고 역탐색과 저장 방향을 구분 |
| 대체 후보 관계 / 대체 승인 관계 | 후보를 승인으로 동치 처리하지 않음. 검토 없는 `owl:sameAs`·`equivalentClass` 금지 |

예: `InstallationEvent —usesLot→ PartLot`, `InstallationEvent —installedOn→ BoardUnit`. 이 명시 사건 경로로 확인된 사용처를 조회한다. BOM·출하 관계만으로 LOT 장착을 추론하지 않는다. 기존60대는 serial/장착 확인 범위를 UNKNOWN으로 남긴다. Graph 조회 결과에는 사용 경로·근거·시간·버전·추론/합성 상태를 함께 반환한다.

## 8. 기존 분석 도구의 이식성

원본 분석 코드는 참고자료다. 이번 인계에서 수정·실행하지 않았으며, Cloud에서 바로 실행 가능하다고 인증하지 않는다.

| 도구 | 확인된 의존성·주의 | 개발 시 조치 |
|---|---|---|
| `build_dataset.py` | `parents[3]` workspace 구조, normalized L1 및 v1.1 baseline 상대경로. 출력 덮어쓰기 | 입력/출력 경로를 명시한 새 변환기로 이행하고 원본 유지. 초기/명령/기대값 분리 |
| `build_ontology.py` | v1.3 bundle + workspace의 v1.1 `data/graph.json`. 출력·검증 파일 생성 | 재현 입력 manifest와 경로 인자를 사용. 실제 엔진 실행은 별도 환경 증거 |
| `ontology-requirements.txt` | 원본 분석 환경에서 rdflib7.6.0, pyshacl0.40.2, owlrl7.6.2 지정 | 존재/설치/호환 검증 후 lock. 앱 전체 dependency가 이미 고정됐다고 주장하지 않음 |
| `prepare_visual.py` | 개발자 로컬 시각화 HTML 절대경로 | 정식 앱 그래프 컴포넌트와 데이터 API로 대체; 경로 치환만으로 구현 완료 아님 |
| `check_visual.cjs` | macOS의 Playwright 위치와 Google Chrome 실행 경로 고정 | Cloud의 실제 설치 패키지/브라우저로 검사 설정 작성. 기존 통과 결과를 Cloud 통과로 복사하지 않음 |

## 9. 데이터 준비의 수용 기준

아래는 전체 계약이다. 현재 실행은 원본 무결성, INITIAL 기초수량·미래 사실 차단, 전체 스키마 보존, 같은 버전의 PostgreSQL/RDF/Neo4j 조회 slice를 확인했다. 원문 BOM 파싱·검수, 전체 적용 소요·입하/IQC, 후속 이행·전체 CQ와 실제 AI를 이 결과로 통과시키지 않는다. 현재 인스턴스18노드/11관계와 전체 카탈로그52클래스/74관계/79shape는 서로 다른 범위다.

1. 모든 원문·이전 fixture의 hash 보존과 manifest 대조. 누락된 입력은 이름·영향 Task·대체 가능 여부로 보고한다.
2. 초기 DB에서 `100/60/50/35/32`, 잔여68, 가용20, BOM 미등록을 재조회한다. 원천 v131와 서버 버전을 구분한다.
3. 초기 DB·그래프·검색에서 미래 승인·신규 양품40·최종도착100·EXPECTED 정답이 조회되지 않는다.
4. 원문74행과 적용62/설정1/제외11을 각각 추적한다. 미검수·모호성·단위가 계산에 미치는 영향을 표시한다.
5. 기본40/부족20, 계획43/부족23 및 다른 부족3품목을 같은 snapshot에서 검증한다.
6. 입하 전·검사대기·부분합격·합격 후 가용의 수량이 보존된다. 품목73과 LOT50/23을 분리한다.
7. 중복 명령·구버전·자기승인·권한 회수·응답 유실을 검증하고 원장 부작용이 중복되지 않는다.
8. 같은 run/시간/권한/버전의 RDB·RDF·Neo4j·AI 구조화 결과를 대조한다. 투영 미준비는 명시적으로 표시한다.
9. 후속 전체 실행에서 중간3→2→1 및 최종100/100과 기한을 검증한다. 조회 시점 이후 사건의 유입을 거절한다.
10. 기존 CQ20개와 추가 후보를 보존하고 해당 미구현 사례는 NOT_RUN으로 남긴다. 오프라인 fixture 검증을 서비스·실제 AI 인수로 보고하지 않는다.

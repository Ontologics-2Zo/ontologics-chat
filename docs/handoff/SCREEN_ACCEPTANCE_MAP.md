# MK-S2 화면 → 업무 구현 → 검증 대응표

작성일: 2026-11-08 · 대상: `Ontologics-2Zo/ontologics-chat` · 상태: **INITIAL 서버 조회 범위 검증 / BOM 연결 코드·합성 검사 확인 / 실제 원본 실행 BLOCKED / 전체 서비스 인수 미완료**

현재 실행 범위는 [BOM 실행 기록](SERVICE-BOM-20261108.md), 검증된 초기 조회 범위는 [INITIAL 실행 기록](SERVICE-INITIAL-20261108.md)을 따른다. 과거 UI-TABS 기록은 보존 화면과 당시 참조 코드의 증거다. 기존 `web/` 직속 7파일은 보존하고 이후 업무 화면은 `web/mks2/`에 연결한다. MK-S2는 서버 원장·투영·도구를 사용하며, 참조 fixture는 보존된 `현재 구현` 탭에만 사용한다. `확인 목록`의 수동 체크와 Task 구현·화면 연결·실행 검증 상태를 구분한다. 화면 확인만으로 업무 쓰기·원장·실제 AI를 완료 처리하지 않는다.

MK-S2의 디자인·두 주화면·핵심 동선을 프론트엔드 기준으로 유지한다. 목업의 브라우저 상태·정해진 응답·타이머·역할 선택을 실제 원장·Agent·인증 구현으로 간주하지 않는다. 기존 v1.7의 전체 기능은 보존하고, 현재 1차 범위는 **MK-S2 자재 확보 흐름 서비스화**다. 생산·출하·도착 현황 조회를 유지하되, 후속 생산·출하·도착 사건을 1차에서 자동 실행하지 않는다.

## 1. 기준과 변경 경계

| 근거 | 적용 방법 |
|---|---|
| SRC-V17-01 · 공식 v1.7 요구사항 §3~11 | 식별자·수량·권한·승인·온톨로지·AI·수용 기준. 기존 요구를 화면 모양 때문에 삭제하지 않는다. |
| SRC-V17-02 · 공식 v1.7 화면설계 §6 및 공통 계약 | SD-001~036, PNL-01~24는 기능 추적 ID다. 같은 수의 메뉴·페이지를 새로 만들라는 뜻이 아니다. |
| SRC-V17-03 · 공식 v1.7 개발설계 §12 | T00~T23 선행·완료 게이트. 실제 구현 순서는 [구현 작업표](IMPLEMENTATION_TASKS.md)를 따른다. |
| SRC-PLAN · 최신 범위·실시간 계획 | 현재 우선순위와 원장 사건 중심 갱신. v1.7 기능 삭제가 아닌 단계별 배치다. |

근거의 실제 위치·해시는 [자료 인덱스](SOURCE_INDEX.md)의 SRC-V17-01/02/03, SRC-PLAN, SRC-AI, SRC-MKS2를 따른다. 사용자가 공개 저장소 유지와 원본 별도 보관을 선택했으므로 원문은 이 저장소에 복사하지 않는다. Cloud에는 필요한 원본을 저장소 밖 `PRIVATE_INPUT_ROOT` 아래에 별도 제공해야 하며 로컬 첨부가 자동으로 이동하지 않는다. 원본을 받지 못한 상태에서는 픽셀·동선 일치 검증을 `SOURCE_UNAVAILABLE`로 남기고 새 UI를 임의로 확정하지 않는다.

### 유지할 것

- 운영 대시보드 / 온톨로지·질의의 두 진입점, 표·견적 카드·상세 드로어·오른쪽 AI 패널.
- 회차별 이행 단계, 자재 충족 비교, 확보 진행, **수입검사**, 원장 사건, 관계 선택과 근거 이동.
- 업무 대상 선택 → 표·그래프·AI가 동일 대상을 참조하는 흐름.

### 필요한 최소 보완

- 조회중·빈 결과·부분 범위·미확인·권한 없음·실패·투영 대기·과거 기준의 구별.
- 서버 승인·반영 결과, 정확 버전·근거, 재시도/대사와 관련 상태 줄.
- BOM 미연결·미검수 표시, 기본/예측안의 나란한 비교, 대시보드 통합 상태·이상징후. 계산 가능한 일부 품목을 먼저 보여줄 때도 원본 전체 행·미확인 개수를 유지하고 `N개 품목 기준 시연 · 가정 수량·재고 적용` 범위를 표시한다.
- 원본의 추천 질문 즉시 실행은 공식 AI-06에 맞춰 **질문 초안 채우기 → 명시적 전송**으로 바꾼다. 선택·필터·확대·접기는 모델 호출과 업무 쓰기를 발생시키지 않는다.

새 화면이 필요한 후속 업무는 별도 기능 범위를 기록한다. 단순 화면 연결을 위해 v1.7의 계산·권한·승인 규칙을 약화하지 않는다.

1차는 관련 기능의 수직 흐름을 먼저 구현한다. `후속`은 삭제·선택사항 전환이 아니며 T23 전체 인수의 잔여 범위다. 한 화면에 1차/후속 기능이 섞이면 각각의 완료 상태를 관리한다.

## 4. 실시간 상태 반영의 화면 계약

1. 확정 업무 변경은 transaction·audit·outbox를 거쳐 서버 원장 사건으로 전달한다. 사건 목록·수량·관련 표를 갱신한다. RDF/Neo4j 준비 전에는 투영 대기를 표시하고 혼합 버전 결과를 만들지 않는다.
2. 채팅에는 현재 선택 대상뿐 아니라 **해당 답변이 참조한 수요·품목·LOT·구성·일정·규칙의 의존성**을 검사해 영향이 있는 변경만 표시한다. 무관 사건은 권한 범위 내 원장 사건 목록에서 확인할 수 있다.
3. 상태 줄은 결정적 비교 결과다. `입하23 · 검사대기 · 가용 변동 없음`, `합격23 · 사용가능 전환 반영`처럼 업무 의미를 구분한다. 수입검사 상태를 알람으로 대체하지 않는다.
4. 과거 답변·What-if는 당시 버전으로 남긴다. `기준 이후 관련 변경 있음`과 재분석 행동을 제공하고, 사용자가 전송한 새 질문은 최신 허용 근거로 실행한다. 생성 중 변경도 조용히 최신 답처럼 덮어쓰지 않는다.
5. 수신 중복·역순·권한 회수·연결 단절·재개·계정 전환을 시험한다. 구독별 권한, 증분 전달, 변경 합치기, 페이지 제한과 부하 측정으로 자원 사용을 관리한다. 부하가 없다고 가정하지 않는다.

## 5. 대시보드 이상징후의 의미

| 분류 | 대표 검증 사례 | 화면 처리 |
|---|---|---|
| 데이터 오류 | 출하2인데 해당 출하의 도착3 | 오류 근거·불일치 수량, 반영 차단/정정 검토 연결 |
| 업무 규칙 위반 | 검사대기 LOT를 사용가능 재고로 처리 시도 | 정책 ID·검사 상태·차단 결과, 검수 업무 연결 |
| 조건부 예측 위험 | 현재 승인된 공급·생산·운송 가정으로 도착기한 초과 | 가정 버전·제약·예상 일정·대안 표시; 실제 지연 확정과 구별 |
| 검토 필요 | BOM 매핑·능력·검사·운송 근거 누락 | 부족한 자료와 확인 담당/다음 행동 표시; 부족0·기한충족으로 대체 금지 |

위 4종의 표시 방향은 사용자 확정 사항이다. 품목/일정별 구체적인 탐지 임계값과 새 업무 정책은 별도 검토·버전 관리한다.

## 6. 화면 인수에서 반드시 남길 증거

각 행은 `requirement_id, task_id, screen/selection_context, case_id, actor_scope, read_snapshot_id, ledger/projection/ontology/rule_version, command, environment, result, evidence_ref`를 연결한다. UI 캡처만으로 서버 수량·권한·지속 저장을 통과 처리하지 않는다. 실제 서버/DB 검사와 UI 왕복을 함께 확인한다.

- 동일 질문의 직접 도구·UI·AI 구조화 결과를 비교한다. 문장의 완전 일치가 아니라 대상·수량·단위·판정·조건·근거·버전 일치를 검증한다.
- BOM/견적/구매/검사마다 최소 정상·근거 부족·권한 위반·버전 충돌·중복/응답 유실 사례를 연결한다.
- 단순 스타일 변경마다 전체 비용 실험을 반복하지 않는다. 영향받은 업무 후조건·상태·근거와 공통 회귀를 검증한다.
- 사용자 승인 전의 시연 가정은 합성 설정으로 남긴다. v1.3 최종 도착 상태나 합성 승인 사건을 서비스 초기 상태·실제 승인으로 재사용하지 않는다.

전체 검증 구분과 보고 조건은 [인수 게이트](ACCEPTANCE_GATES.md)를 따른다.

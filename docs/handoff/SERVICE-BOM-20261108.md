# SERVICE-BOM-20261108 — 실제 BOM 원본 등록과 MK-S2 소요 조회

2026-11-08 · 작업 브랜치 `codex/mks2-bom-integration` · 기준 `cc14606` · **코드 구현·합성 검증 확인 / 실제 원본 경로 BLOCKED**

이 기록은 사용자가 요청한 T00~T23 작업표의 적용 체크와 실제 BOM 접수 → 검토 → 정확 버전 승인 → 원장 반영 → 소요·부족 조회의 실행 범위를 남긴다. 이전 [INITIAL 실행 기록](SERVICE-INITIAL-20261108.md)의 결과와 이번 변경의 검증을 구분한다. Cloud의 Docker 자원 제한 강제가 지원되지 않아 실제 원본 경로는 차단했다. 코드·독립 합성 자료 검사와 실제 BOM 반입·승인·원장 반영 결과를 분리하며, 현재 실제 원본 파싱/반입은 0건이다. 실제 원본 bytes/hash를 확인한 접수 요청은 별도 시험 schema에서 Runner gate에 의해 거절됐고, BOM 문서·출처·원장 사건·outbox 건수가 전후 동일했다.

## 현재 실행 차단 사유

실제 Docker capability 조회에서 `CgroupDriver=none`, `MemoryLimit=false`, `PidsLimit=false`, `CPUCfsQuota=false`가 확인됐다. 이미지 빌드 성공은 이 자원 제한을 보장하지 않는다. Runner는 `RUNNER_ENFORCEMENT_UNAVAILABLE`로 닫히며 이 환경에서 실제 BOM 원문을 파싱하거나 호스트 파서로 우회하지 않았다.

- T08의 실제 제한 Runner 수용과 그 선행을 요구하는 T09의 원본 접수는 **BLOCKED**다.
- BOM 도메인·계산·UI 코드는 독립 합성 자료로 검증했다. 합성 테스트 통과를 실제 원문 처리·등록 승인으로 보고하지 않는다.
- 실제 74행 원본 등록·검토·승인·반영과 현재 BOM 기준 소요/부족의 사용자 확인은 아직 수행하지 않았다. 표시 우선순위는 계산 가능한 일부 품목을 먼저 보여주는 권고로 정리했지만, 이를 사용자에 의한 실제 구성·기술 데이터 승인으로 기록하지 않는다.
- 지원되는 Mac Docker Desktop 등에서 같은 이미지의 enforcement probe가 통과한 뒤 실제 경로를 이어간다. 사용자 Mac에서 이전 main이 실행됐다는 별도 기록은 이번 BOM 브랜치 검증을 대신하지 않는다.

## 적용 범위와 보존 기준

- `web/` 직속 화면 7파일은 `b3ee599` 보존본이다. 업무 화면 변경은 `web/mks2/`, 작업 확인은 기존 `확인 목록` 탭에만 적용한다.
- 기존 DB·원장·원본을 초기화하지 않는다. 추가 migration, 별도 BOM 문서·출처, 승인 사건과 새 원장 버전으로 연결한다. 과거 snapshot과 승인 근거를 보존한다.
- 실제 BOM 원본은 Git 밖에서 읽고 제한된 Runner로 처리한다. 원문 파일·파싱 결과·DB·캡처·개인 경로·자격증명은 공개 Git/PR에 넣지 않는다.
- 원본 등록 승인은 **해당 원문의 출처·행·검토 내용을 원장에 기록하는 승인**이다. 기술 검수, 품목 동일성, 단위, 실장 판단, 현장 재고가 모두 확정됐다는 뜻이 아니다.
- 실제 BOM의 행과 기존 합성 초기 운영 잔액을 구분한다. 미확인 매핑·단위·재고는 `UNKNOWN`이며 0으로 대체하지 않는다. 추가 양품 목표 40과 수율 94%를 가정한 투입 43은 조건을 표시하고 비교한다.
- 전체 온톨로지 구조와 원본 전체 행을 보존한다. 제외·설정·미확인 행도 삭제하지 않으며 전체 충족 판정에서 누락하지 않는다.

## 실제 자료에서 남아 있는 검수 항목

- 대표 L1 원본은 전체 74행 보존 대상이다. 파일명과 내부 시트명의 구성 표기가 서로 달라 기술 검수에서 해소해야 한다.
- 62적용/1설정/11비실장과 추가 57개 품목·재고는 기존 `proposed_demo_default`다. 원문 사실이나 현장 승인으로 승격하지 않는다.
- 기존 5개 품목 매핑도 합성 운영 원장·검수 상태와 함께 취급한다. 계산에 사용한 행별 결정과 근거를 정확 버전 승인 내용에 포함한다.
- 미확인 항목이 있으면 확인된 항목의 조건부 계산과 전체 판정 보류를 함께 표시한다. 원본 등록 완료만으로 전체 자재 확보·제조 가능성을 확정하지 않는다.

## 화면에서 먼저 보여줄 범위와 추가 입력

사용자의 후속 질문에 따라 **원본 전체 74행을 보존하고, 기존 5개 후보 품목의 조건부 계산을 먼저 보여주며 나머지 행은 원본 상세에서 펼쳐 확인하는 표시 방식**을 권고한다. 이는 화면 우선순위에 대한 구현 선택이며 미확인 행 삭제나 새로운 실제 데이터 승인으로 처리하지 않는다. 현재 실제 원본 경로가 차단된 상태에서 이 5개를 실제 BOM 계산 검증 완료로 표시하지 않는다.

표시는 데이터에 맞춰 `N개 품목 기준 시연 · 가정 수량·재고 적용`과 전체/계산/미확인 행 수를 함께 보여준다. 제외·설정·미확인 행을 접어 보여도 원문·그래프·검토 범위와 전체 판정에는 남긴다. 전체 기준이 확인되지 않으면 일부 부족 수량이 0이어도 전체 확보를 확정하지 않는다.

실제 소요·부족을 확정하려면 다음 입력이 필요하다.

| 필요한 입력 | 확인할 내용 |
|---|---|
| 제품 구성·개정 | 파일명/시트명 구성 충돌의 해소와 적용할 실제 개정 |
| 행별 품목·단위·실장 | 사내품목과 원문 행의 대응, 단위, 보드당 수량, 적용/설정/비실장 여부 및 검수 근거 |
| 재고 기준 | 기준일과 품목/LOT별 재고, 자기/타수요 예약, 검사대기·보류·사용 가능 수량 |
| 생산 목표·수율 | 실제 추가 양품 목표와 계획 수율의 근거. 94%는 기존 조건부 계획 가정이며 보장 수량이 아님 |

합성 집계 사례는 같은 품목의 두 행에 보드당 1개와 2개를 명시적으로 적용했다. 목표40에서 소요120·가용20·부족100, 조건부 투입43에서 소요129·부족109를 서버와 화면에서 대조했다. 나머지 두 행은 UNKNOWN으로 유지했다. 이는 계산 계약 검증용 합성 사례이며 실제 L1 BOM 수량 결과가 아니다.

기존 DB 비교 대상은 `ledger_state`, `ledger_events`, `service_snapshots`, `opening_imports`, `documents`, `outbox`다. `ledger_events`에는 새 nullable `bom_document_id` 열이 추가됐으므로 기존 내용 hash는 이 새 열을 제외한 동일 필드로 비교했다. 승인된 사실·과거 버전·잔액을 지우거나 바꾸지 않았다.

기존 INITIAL의 소스 155개 무결성, 서비스 124개·브라우저 27개 검사는 당시 코드와 범위의 증거로만 재사용한다. 신규 BOM 결과를 포함한 통과 수로 표시하지 않는다.
